# Technician joining contract

One application remains `pending` until central rejection or a single approval. Routing is `matched`, `unmatched`, or `all_declined`; legacy routing may be null. Branch nominations are `eligible`, `declined`, `approved`, or `closed`. A branch decline never rejects the application.

Public multipart `POST /api/v1/serviceman/auth/registration` retains existing identity/contact/image fields and requires `work_latitude`, `work_longitude`, `location_source` (`gps`/`map_pin`/`manual`), and accepted `privacy_consent`. Optional fields: `work_location_label`, `city`, `district`, `experience_years`, `preferred_service_ids[]`, `note`. Assignment and reviewer fields are prohibited. Response 201 contains `id`, `status`, `routing_status`, `matched_branches_count`, `branch_name`, `rejection_reason`, `submitted_at`, `reviewed_at`. No User exists before approval. Existing `POST .../auth/application-status` uses phone/password in the body and returns the same sanitized content (200). Both have IP and hashed phone rate limits.

Authenticated provider endpoints under `/api/v1/provider/technician-applications`: GET list (`status=pending|closed|all`, page, limit<=100), GET `unread-count`, GET `notifications`, POST `notifications/{uuid}/read`, GET `{uuid}`, GET `{uuid}/attachments/{profile|0|1|2}`, POST `{uuid}/approve`, POST `{uuid}/decline` (`reason`). The server resolves the branch and checks `technicians.manage`. List content is `{applications: paginator, unread_count, recruitment_enabled}` with sanitized `applications.data`; detail content includes authorized contact/location/identity fields, `branch_status`, `identity_images_count`, `serviceman_id`, `preferred_services` (id/name), `can_approve` and protected attachment endpoints. Lists omit identity numbers, documents, precise coordinates and passwords. Notification bodies contain only application ID, event, read and creation times. Details mark the current recipient's notifications read.

Errors: 401 invalid applicant credentials/session, 403 missing permission, 404 outside record scope, 409 already decided/no longer eligible, 422 validation, 429 throttled. Approval always locks the central application first and revalidates live branch eligibility. A second approval returns 409 even for the winning branch. Central override is restricted to super-admin and requires a recorded reason; ordinary central approval requires a current geographic nomination. Central rejection is available to global reviewers only.

Documents remain on a private disk, streamed through scoped authenticated endpoints with private/no-store/nosniff headers. Legacy records use their original local disk. Approved technicians retain a protected application reference in their existing profile views. Push is recorded after commit in a separate optional outbox channel with type `technician_application`; public status is the applicant's source of truth.

`GET /api/v1/serviceman/auth/application-options` returns up to 200 active service IDs/names for optional preference chips (IP limited to 20/minute). No location preview endpoint is introduced; server matching is authoritative at submission and approval.

All application API errors use `{response_code: technician_application_error, message, content: null, errors}`; validation errors are keyed by field. Rate limit headers are preserved. The existing total-upload-size renderer remains responsible for HTTP 413.
