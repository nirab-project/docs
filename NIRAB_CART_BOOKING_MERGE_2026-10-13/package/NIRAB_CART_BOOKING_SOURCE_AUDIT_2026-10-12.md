# NIRAB — التدقيق البرمجي وإصلاحات السلة والحجز والدفع

**التاريخ:** 12 أكتوبر 2026  
**الحالة:** إصلاحات مصدرية جاهزة للمراجعة والدمج؛ **غير منشورة إلى الإنتاج**، ولم تُجر اختبارات HTTP/MySQL/Flutter تشغيلية.  
**نطاق العمل:** ملفات ZIP الأربعة التي أُرفقت بمشروع NIRAB، وليس التقارير فقط؛ فُكّ واستعرض مجموع **3,203 ملفات**. راجعت مسارات السلة والتسعير وتثبيت سعر الحجز والفروع والمدفوعات وتطبيقات الأطراف الثلاثة. غُيّر **11 ملفًا** في Backend وتطبيق العميل/الويب، ولم تُغيّر ملفات تطبيق الفرع والفني.

## 1) الحكم التنفيذي

الخطأ 500 عند إضافة السلة **للزائر** له مرشح قوي واضح في السورس: بعد كتابة السلة يستدعي `CartController::addToCart` دالة `Guest::firstOrCreate(['guest_id' => ...], ['ip_address' => ...])`؛ ونموذج `Guest` يُعرّف `$fillable = []`، فتوليد سجل ضيف جديد بهذه الطريقة معرض لاستثناء `MassAssignmentException`، ما يؤدي إلى فشل المعاملة. ويُنشئ `PaymentPrincipal::issueGuest` أصلًا سجل Guest بمعرّف صادر من الخادم؛ لذلك أزيلت محاولة الإنشاء المكررة وربطت ملكية السلة برمز الجلسة الموقع الصادر من الخادم.

**الحد الفاصل:** هذا سبب *مؤكد كمخالفة مصدرية ومنطقية لمسار الزائر*، وليس إثباتًا أن **استثناء الإنتاج المعيّن** هو نفسه، إذ لم تُقدَّم سجلات الخطأ الحيّة لحظة تنفيذ POST. إن كان الخطأ يحدث للمستخدم المسجل أيضًا، فلا يكفي هذا الإصلاح لتفسيره؛ ينبغي مراجعة سجل Laravel وقاعدة MySQL ومخطط الخدمات لحظة الخطأ.

### نقاط مصدرية لم أعد فتحها كعيوب

- `BookingAmendmentService::lineIdentifier` ومعالجة حذف بندين متشابهين موجودة في Backend الحالي؛ تطبيق الفرع والفني يرسلان `detail_id` و`booking_repeat_id` عند الحاجة. لم أجد في هذه المسارات سببًا يوجب الرجوع لإصلاح A06 السابق.
- `BranchCheckoutService` يحتوي ربط `checkout_snapshot_id` وسجل نتيجة المحاولة وأقفال `lockForUpdate`، ومراجعة إعادة التسعير، والتأكد من عدم تغير عناصر السلة. وجود هذه الضوابط لا يثبت اجتياز اختبار التزامن على MySQL.
- لم أغيّر التسعير نفسه أو منطق MySQL Spatial أو أرصدة المحفظة أو callbacks بوابات الدفع؛ تلك مناطق تحتاج قبولًا تشغيليًا مستقلًا.

## 5) ما يجب اختباره على مشروع المالك قبل نشر أي تعديل

لا تنفذ هذه الاختبارات على حجوزات العملاء الفعلية أو بوابات دفع حقيقية. بما أن بيئة Dokploy الحالية مرحلة ما قبل الإطلاق، استخدم حسابات وفروع وخدمات اختبارية معلّمة بوضوح، ونسخة احتياطية حديثة، وبوابات دفع في وضع الاختبار حيثما كان ذلك مدعومًا.

## 6) أوامر قراءة فقط على خادم Dokploy للتحقق من سبب 500 الفعلي

```bash
CID=$(docker ps -q --filter name=nirab-production-nirab-backend | head -n1)
[ -n "$CID" ] || { echo 'Backend container not found'; exit 1; }

docker exec "$CID" sh -lc 'cd /var/www/html && php artisan route:list --path=api/v1/customer/cart --no-ansi'
docker exec "$CID" sh -lc 'cd /var/www/html && php artisan route:list --path=api/v1/customer/booking --no-ansi'

docker exec "$CID" sh -lc 'cd /var/www/html && php artisan migrate:status --no-ansi | tail -n 90'

# بعد إعادة محاولة الإضافة لمرة واحدة:
docker exec "$CID" sh -lc 'cd /var/www/html && for f in $(ls -t storage/logs/*.log 2>/dev/null | head -n 2); do echo "=== $f ==="; tail -n 250 "$f"; done'
```

قارن **وقت الخطأ، وHTTP URL، ونوع الاستثناء، وملف PHP والسطر**. أخفِ tokens وأرقام الهواتف وأسماء العملاء وبيانات الدفع قبل مشاركة السجلات. لا تشغّل `migrate`, `rollback`, `optimize:clear` أو تعديل جداول الإنتاج بغرض التشخيص الأولي.

## 7) طريقة تطبيق الإصلاحات لدى الوكيل

احفظ النسخة الحالية من كل مستودع في Commit أو branch، ثم استخدم **ملف Patch الخاص بالمستودع** دون إعادة ترتيب المسارات:

```bash
# داخل جذر مستودع Backend:
git apply --check NIRAB_CART_BOOKING_BACKEND_FIXES_2026-10-12.patch
git apply NIRAB_CART_BOOKING_BACKEND_FIXES_2026-10-12.patch

# داخل جذر مستودع customer user-app-web:
git apply --check NIRAB_CART_BOOKING_CUSTOMER_FIXES_2026-10-12.patch
git apply NIRAB_CART_BOOKING_CUSTOMER_FIXES_2026-10-12.patch
```

**انتبه:** صُممت التعديلات لنسخة ZIP التي فُحصت. إذا تغيّر HEAD في المستودعات بعد تصدير هذه النسخة، قد يفشل Patch؛ حينها ينبغي تطبيق التعديل يدويًا بعد مراجعة الفروق، لا فرض `--reject` أو استبدال الملف الأحدث كاملًا من ZIP. الأفضل مراجعة diff ثم `php -l`, `flutter analyze` و`flutter build web` محليًا وSmoke Tests يدويًا على متصفح العميل وهاتف Android حقيقي (ليس محاكيًا). لا تنشر قبل نجاح توافق Backend/الويب/العملاء والتأكد من الترحيلات وحالات Modules الفعلية.

## 8) قرارات النشر وحدود العمل

- **لا يوجد Commit أو Push أو Deploy منفذ من هذه المراجعة.** الملفات المعدلة والـpatches للتسليم والمراجعة، ولم يُلمس MySQL أو Dokploy.
- **لم نثبت أن خطأ 500 الحالي قد انتهى في الإنتاج.** إذا تكرر بعد الدمج، التقط Laravel exception وبيانات الطلب المختصرة؛ قد يكون منشؤه مخطط الجداول، Module معطل، بيانات خدمة، أو منطق تسعير يختلف عن الملفات المفحوصة.
- **لا تغيّر ترحيلات أو بنية قاعدة البيانات في هذه الدفعة.** جميع التعديلات الحالية ضمن العقود والـControllers والعميل.
- **هناك حاجة لاختبارات مدفوعات وتزامن حقيقية** تشمل Tap/Tabby/Tamara وWebhooks والأرصدة/المحفظة وOdoo، باستخدام Sandbox ونسخة اختبارية من قاعدة البيانات؛ الفحوص الساكنة وحدها لا تعادل ذلك.
- يُرجى مراجعة تغييرات المصادقة للزائر قبل إطلاق إصدار جوال قديم؛ النسخة القديمة التي لا ترسل `X-Guest-Payment-Token` ستتلقى 401 بعد فرض التحقق الجديد. أصدر تحديث العميل والويب منسقًا مع Backend، وخطة توافق للنسخ القديمة إن كانت منشورة للمستخدمين.
