## دليل قراءة الوثيقة

1. اقرأ الحدود والقرارات في الأقسام 1–3 قبل تعديل أي ملف.
2. راجع مصدر البيانات والتوجيه في الأقسام 4–6؛ هذه هي نقاط منع التراجع الوظيفي.
3. نفّذ المراحل في القسم 7، ولا تتجاوز بوابة قبول مرحلة دون تسجيل وضعها.
4. اتبع بروتوكول الهاتف الحقيقي في القسم 8، والفحوص في القسم 9.
5. أغلق مصفوفة القبول والتسليم في الأقسام 10–12، واستعن بمرجع الملفات والصور في الملاحق.

كل اسم ملف تحت عنوان «مقترح/جديد» هو مطلوب إنشاؤه عند الحاجة، وليس ادعاءً بأنه موجود حاليًا. المسارات في ملحق المصدر موجودة فعلًا في الأرشيف المفحوص. المرجع المحلي الأحدث عند المستخدم قد يتضمن تغييرات إضافية؛ يجب مطابقتها أولًا، لا استبدالها بنسخة الأرشيف.

# 1. الهدف وحدود التفويض

## 1.1 النتيجة المطلوبة

تطبيق عميل واضح وهادئ: موقع الخدمة ظاهر، الوصول إلى التصنيفات مباشر، تفاصيل الخدمة قابلة للقراءة، الإجراء التالي مفهوم، ورحلة الطلب متصلة بصريًا. يجب أن يبدو منتج NIRAB واحدًا على الهاتف والويب، لا مجموعة صفحات متفرقة أو قالب سوق مزودين.

النجاح ليس تغيير اللون والزوايا فقط. النجاح هو إعادة تنظيم الواجهة والمكونات مع بقاء الوظائف التي يعتمد عليها العميل قابلة للوصول والعمل.

## 1.2 ما يسمح بتغييره

- تركيب الشاشات، ترتيب المحتوى، المسافات، الخطوط ضمن العائلات الحالية، البطاقات، الأزرار، النوافذ، القوائم والتنقل المرئي.
- مكونات العرض والثيم والترجمات والأصول البصرية الخاصة بالمشروع.
- تعديلات محدودة في حالة العرض والتوجيه لربط التنقل الجديد، مع توافق الروابط القديمة والحفاظ على حماية الصفحات.
- فصل `Widget` كبير إلى مكونات عرض أصغر، مع بقاء مصدر الحقيقة الوظيفي نفسه.
- إصلاح خلل عرض أو تنقل يمنع إعادة التصميم، بعد توثيق سببه وفحص الاستدعاءات المتأثرة.
- فحوص ساكنة واختبارات Widget/Unit صغيرة، وتشغيل تطبيق العميل واختباره على الهاتف الحقيقي، وبناء الويب محليًا.

**توجيه الهاتف الحقيقي في هذه المحادثة يسمح بتشغيل واختبار تطبيق العميل ضمن هذا النطاق، حتى لو وُجدت تعليمات سابقة لمراحل أخرى بالاكتفاء بالفحوص الساكنة. لا يمد هذا الإذن إلى تشغيل باك إند جديد أو migrations أو اختبارات ثقيلة.**

## 1.3 الممنوعات

- لا تعديل لمشروعات Backend/Admin أو Branch/Provider أو Technician/Serviceman ضمن هذه المهمة.
- لا migrations، ولا إعادة إعداد قاعدة البيانات، ولا تغيير MySQL 8 + Spatial.
- لا تغيير لحساب الضرائب والخصومات والمبالغ أو حالات الحجز أو قرار نجاح الدفع، ولا تغيير عقود API أو سياسات المصادقة.
- لا استبدال GetX بإطار آخر، ولا إعادة كتابة المستودعات أو Controllers الوظيفية لمجرد التنسيق.
- لا ترقية Flutter/Dart أو الحزم، ولا تغيير `pubspec.lock` لمجرد بدء العمل. أي عائق بيئة يوثَّق بدل علاجه بترقية جماعية.
- لا تعديل للأسرار، التوقيع، package/application IDs، Firebase، Google Sign-In، مفاتيح الخرائط، بوابات الدفع، أو إعدادات الإنتاج.
- لا تشغيل محاكي، ولا تنزيل صور أنظمة محاكاة، ولا تغيير إعدادات التطبيق لجعله يعمل على محاكي.
- لا تنفيذ دفع حقيقي، استرداد، شراء باقة من محفظة حقيقية، إلغاء حجز عميل، حذف حساب أو تعديل بيانات إنتاج لأجل الاختبار.
- لا `git reset --hard`، ولا `git clean -fd`، ولا حذف/استبدال عمل المستخدم، ولا force push.
- لا رفع إلى GitHub ولا دمج/نشر تلقائي؛ قد يؤدي `push` إلى تشغيل Auto Deploy. الإذن الحالي للتعديل المحلي والتوثيق فقط.
- لا نسخ شعار المنافس أو صوره أو نصوص عروضه أو ضماناته إلى التطبيق.
- لا إخفاء خطأ وظيفي أو إرجاع نجاح وهمي حتى تكتمل لقطة التصميم.

## 1.4 إدارة الفرع والنسخة المحلية

اتجاه المشروع السابق هو `main` بعد إغلاق الدمج الوظيفي. افحص الفرع وHEAD والحالة المحلية قبل العمل. اعمل على `main` المحلي الصحيح إذا كان متاحًا، ولا تعِد دمج `staging` أو تعِد فتح مراحل UX-01–UX-06 المغلقة.

إذا كان الفرع مختلفًا أو توجد تغييرات غير محفوظة: حدد الملفات المتعارضة، واحفظ عمل المستخدم كما هو. لا تنفذ تبديلًا أو stash أو reset آليًا. اطلب توجيهًا فقط عندما يوجد تعارض حقيقي يمنع المتابعة. استخدم commits محلية خاصة بهذه المهمة، وأضف ملفاتها صراحة بدل `git add .` غير المراجع.

# 2. القرارات التصميمية التي يبدأ بها التنفيذ

هذه قرارات البداية، وليست قائمة خيارات يعيد الوكيل طرحها على المستخدم. تُعدّل مرة واحدة فقط عند نقطة الاعتماد المبكرة إن لزم.

| القرار | التنفيذ المعتمد مبدئيًا |
|---|---|
| الهوية | NIRAB CLEAN؛ الشعار والألوان الحالية، لا ألوان المنافس المنسوخة |
| الخطوط | Cairo للعربية وRoboto للإنجليزية؛ الحفاظ على دعم اللغات الأخرى الموجود |
| اتجاه القراءة | RTL عربي وLTR إنجليزي، دون قلب الصور أو الشعارات أو الأرقام عشوائيًا |
| الرئيسية | رأس مختصر + الموقع + مدخل بحث صغير + بانر + شبكة تصنيفات + محتوى ثانوي محدود |
| شريط الهاتف | أربع وجهات مرئية: الرئيسية، حجوزاتي، الباقات، حسابي |
| السلة | وجهة مستقلة محفوظة، ومدخل دائم واضح مع عداد، وليست زرًا خامسًا في الشريط |
| العروض | تبقى قابلة للوصول من الرئيسية/الحساب ومسارها الحالي |
| الباقات | باقات زيارات العميل الموجودة؛ ليست «عقودًا» جديدة ولا اشتراكات فروع |
| الخدمة | قالب موحد مرن، ملخص وتسعير مبكران، صور، وصف ونطاق متاح، أسئلة وتقييمات فعلية |
| الخدمة المسعّرة | تحديد الخيارات عبر التدفق الموجود ثم الإضافة/متابعة الحجز بحسب الحالة |
| عرض السعر | «اطلب عرض سعر» عبر التدفق الحالي؛ لا يمر إلى سلة الخدمات المسعّرة |
| بيانات ناقصة | إخفاء القسم الاختياري أو بديل صادق، لا اختراع محتوى أو سعر أو مدة |
| الويب | تخطيط مناسب للمساحة مع محتوى أقصى 1200، لا هاتف ممدود |
| الاختبار | التطبيق الفعلي على الهاتف المتصل؛ اختبار الويب منفصل ولا يحل محل Android |

## 2.1 ما نأخذه من الصور

نأخذ وضوح التسلسل، وبطاقات التصنيفات، والمساحات الهادئة، والتناسق بين صفحات الخدمات، وحالات الضيف المخصصة، وإمكانية الوصول إلى الإجراء الأساسي.

لا ننقل فراغات الشاشة الضخمة، ولا الفقرات العامة المتكررة، ولا التضارب بين «سعر ثابت» و«معاينة»، ولا أسماء الأقسام التي لا يقابلها عمل حقيقي في NIRAB. الصور توثّق المظهر فقط؛ لا تثبت ماذا يحدث بعد الضغط على الأزرار.

## 2.2 نقطة الاعتماد المبكرة

بعد RUI-01 يُعرض اتجاه واحد، لا ثلاثة اتجاهات بديلة: الرئيسية + خدمة مسعّرة + خدمة عرض سعر. تكون المعاينات من المكونات التي سيعاد استخدامها فعلًا، مع صور على الهاتف الحقيقي ومقابل الويب عند توفره.

موافقة المستخدم الحالية هي على الاتجاه وبدء التنفيذ؛ ليست اعتمادًا مسبقًا لكل تفاصيل المقاسات. لذلك توجد نقطة اعتماد بصرية واحدة قبل التعميم. لا توزّع تصميمًا غير معتمد على عشرات الصفحات ثم تطلب رأيه في النهاية.

# 3. نظام التصميم والمكونات

## 3.1 الألوان

ابدأ من `lib/theme/brand_tokens.dart`؛ هو المرجع المركزي الحالي، لا تنشئ لوحة ألوان موازية داخل الشاشات.

| الدور | القيمة الحالية التي تُحافَظ عليها |
|---|---|
| لون العلامة الداكن | `#044B4A` |
| لون العلامة النعناعي | `#6DC9C9` |
| الإجراء الأساسي في الوضع الفاتح | `#008285` |
| خلفية فاتحة | `#F5FAFA` |
| سطح البطاقات الفاتح | `#FFFFFF` |
| نص أساسي فاتح | `#103B3B` |
| نص ثانوي فاتح | `#526A6A` |
| خلفية داكنة | `#0B1F20` |
| سطح داكن | `#122D2E` |

استخدم أدوار `ColorScheme` والثيم و`CustomThemeColors` للحالات. لا تستخدم النعناعي الفاتح مع نص أبيض صغير دون تحقق. يستهدف النص العادي تباين 4.5:1 على الأقل، والنص الكبير 3:1 وفق تعريف WCAG، والعناصر غير النصية اللازمة لفهم التحكم 3:1 وفق شروطها [T07]، [T08]. لا تعلن التوافق الكامل مع WCAG استنادًا إلى اختبار ألوان فقط.

## 3.2 المقاسات المستهدفة

القيم التالية مواصفة تصميم جديدة كبداية، وليست ادعاءً بأن المصدر يطبقها حاليًا. تضاف كأدوار واضحة أو تضبط في المرجع المركزي مع مراجعة أثرها.

| العنصر | القيمة المستهدفة |
|---|---|
| هوامش الهاتف | 16 وحدة منطقية |
| هوامش الويب | 24 وحدة منطقية |
| مقياس المسافات | 4، 8، 12، 16، 24، 32، 48 |
| استدارة البطاقة الأساسية | 24 |
| استدارة الحقل/الزر | 16 |
| الحد الأدنى لارتفاع التحكم | 52؛ الأزرار الرئيسية 56 |
| مساحة التفاعل الدنيا | 48 × 48؛ حجم الأيقونة المرئي لا يساوي مساحة لمسها |
| عنوان الصفحة | 26، وزن 700 |
| عنوان القسم | 20، وزن 700 |
| النص الأساسي | 16، وزن 400 أو 500 حسب الدور |
| النص الثانوي | 14 |
| عنوان بطاقة التصنيف | 14–15، وزن 600 |
| تسمية التنقل | 12–13، تنمو عند تكبير النص |
| ارتفاع السطر العربي | 1.5 كبداية، دون قص التشكيل |
| الحركة | 180–220ms، خفيفة، مع احترام تقليل الحركة |
| أقصى عرض للمحتوى | 1200 كما في المرجع الحالي |

هذه **حدود دنيا** وليست ارتفاعات صلبة تمنع النمو مع النص. لا تُصغّر الخط آليًا أو تقيد `TextScaler` لتجاوز overflow. متطلبات Flutter للإتاحة تشمل وضوح التحكم والنص ومساحات التفاعل، وتستدعي المراجعة على الجهاز [T04].

احتفظ بتوافق أسماء `robotoRegular` و`robotoBold` المستخدمة حاليًا؛ لا تنفذ إعادة تسمية جماعية. المرجع الفعلي لاختيار عائلة الخط يبقى `BrandTypography` والثيم، بما في ذلك TextFields وDialogs وHTML ووحدات الدفع المحلية.

## 3.3 قواعد التخطيط

- حافظ على نقاط الفصل العامة الموجودة: أقل من 650، ومن 650 إلى أقل من 1300، و1300 فأكثر. لا تغيّر `ResponsiveHelper` عالميًا لمعالجة صفحة واحدة.
- استخدم قيود المساحة الفعلية داخل المكونات؛ يمكن لجزء من الصفحة أن يصبح بعمودين قبل 1300 عندما يسمح عرضه، دون تغيير نموذج التنقل العام.
- على الهاتف: شبكة من ثلاثة أعمدة إذا كان عرض البطاقة لا يقل تقريبًا عن 100 ويسع الاسم؛ وإلا عمودان. عند تكبير الخط قلّل الأعمدة وزد ارتفاع البطاقة بدل تصغير الاسم.
- اسم التصنيف يجب أن يبقى مفهومًا وكاملًا قدر الإمكان. اسم أطول من المعتاد يُلف إلى أسطر إضافية؛ لا تجعل كل البطاقات تعتمد على `childAspectRatio` ثابت يقص النص.
- استخدم `EdgeInsetsDirectional` و`AlignmentDirectional` و`TextAlign.start` حيث تكون الدلالة اتجاهية.
- تجنب وضع تمرير عمودي داخل تمرير عمودي بلا قيود. فضّل صفحة ذات مالك تمرير واحد ومجموعات Sliver/أقسام محددة.
- احفظ حالة التمرير والاختيار عند تبديل التبويب أو تغيير عرض المتصفح، دون إبقاء بيانات حساب سابق بعد تسجيل الخروج.
- صمم لمسًا وفأرة ولوحة مفاتيح؛ زر يظهر عند hover فقط لا يكون المدخل الوحيد لوظيفة [T03].

## 3.4 المكونات المشتركة

استفد من المكونات الحالية قبل إضافة مكونات جديدة. الأسماء التالية **مقترحة للإضافة/إعادة التنظيم**، ويمكن وضع المكونات العامة داخل `lib/common/widgets/nirab/`، والخاصة بالخدمة داخل `lib/feature/service/widget/`.

| المكون | مسؤوليته | ما لا يفعله |
|---|---|---|
| `NirabPageHeader` | عنوان/شعار/رجوع/إجراءات مناسبة للمساحة | لا يجلب بيانات ولا يقرر الصلاحيات |
| `NirabSectionHeader` | عنوان قسم وإجراء ثانوي واضح | لا يفرض «عرض الكل» بلا وجهة |
| `NirabCategoryCard` | صورة أو أيقونة واسم تصنيف وحالة تحميل | لا يختار التصنيف بالـindex الثابت |
| `NirabServiceCard` | ملخص خدمة وإجراء بحسب حالتها | لا يحسب إجمالي الطلب |
| `NirabActionBar` | عرض الإجراء وملخصه دون تغطية المحتوى | لا ينشئ طلبًا أو دفعًا أثناء build |
| `NirabGuestState` | عنوان/رسالة/دخول/رجوع مناسب للسياق | لا يفتح API خاصًا للضيف |
| `NirabAsyncState` | تحميل، فراغ، فشل، إعادة محاولة | لا يحول الفشل إلى حالة فارغة كاذبة |
| `NirabInfoPanel` | ملاحظة تسعير أو تنبيه مرتبط بالبيانات | لا يكرر ضمانًا أو وعدًا غير معتمد |
| `NirabFaqSection` | أسئلة حقيقية قابلة للفتح والإغلاق | لا ينشئ أسئلة عامة لكل الخدمات |
| `NirabServiceGallery` | صور متجاوبة مع fallback ومنع التكرار | لا يكرر صورة واحدة لصنع carousel وهمي |
| `NirabBookingCard` | الموعد والحالة والخدمة والإجراء المتاح | لا يغير حالات الحجز |

احتفظ بعقود `CustomButton` و`CustomTextFormField` و`CustomAppBar` العامة أو عدّل جميع الاستدعاءات المتأثرة ضمن مرحلة واضحة. لا تضف wrapper لكل سطر؛ المكون المشترك مطلوب عندما توجد مسؤولية متكررة قابلة لإعادة الاستخدام.

## 3.5 الصور والحركة والأيقونات

مصدر صور التصنيفات والخدمات هو بيانات النظام الحالية أولًا. اعرض الأيقونات بـ`contain` دون قصها، وصور الخدمة بطريقة مناسبة دون تشويه. لا تطبق صبغة أحادية على صورة فوتوغرافية لإجبارها على شكل أيقونة.

لا توجد حاجة افتراضية لإضافة حزمة أيقونات جديدة. استخدم الأصول المعتمدة أو مجموعة Material متناسقة للبدائل. لا تبنِ تسعة تصنيفات ثابتة لأن المرجع يعرض تسعة؛ اعرض كتالوج NIRAB الفعلي وترتيبه ومعلوماته.

ملفات المنافس داخل `references/competitor/` للمعاينة فقط: لا تسجلها ضمن `pubspec.yaml`، ولا تنقلها إلى `assets/` أو مخرجات الإنتاج. لا تضف فيديو أو صورًا ضخمة أو حركات مكلفة لتقليد بانر.

# 4. مواصفة الشاشات

## 4.1 الرئيسية

**التسلسل:** رأس مختصر → الموقع → بحث صغير → بانر → شبكة التصنيفات → قسم سياقي واحد أو اثنان كحد أقصى.

1. الشعار لا يطغى على المساحة. الضيف يرى ترحيبًا ودخولًا واضحًا؛ العميل يرى تحية ووجهة الحساب. لا تكرر شعارًا كبيرًا داخل الرأس ثم أول المحتوى.
2. اعرض الموقع الحالي الموثوق، أو «حدد موقع الخدمة». حافظ على حالات رفض إذن الموقع وعدم توفر الخدمة؛ لا تعرض مدينة افتراضية وكأنها اختيار المستخدم.
3. احتفظ بوصول البحث الحالي. لا تحول كل بطاقة إلى حقل بحث أو تجعل البحث يستهلك الشاشة.
4. للبانر مساحة متناسبة تقارب 2:1 على الهاتف، لكن لا تقص نصًا مهمًا في أصل البانر. استخدم احتواءً ملائمًا عند اختلاف النسبة. أخفِ مؤشرات التنقل عند وجود صورة واحدة.
5. البانر ينقل إلى الوجهة المسجلة له؛ لا تجعل كل البانرات تؤدي إلى أول خدمة. لا تنشئ خصمًا أو كودًا تجريبيًا في الإنتاج.
6. شبكة التصنيفات تعتمد `CategoryController` وبيانات `CategoryModel`. بطاقة التصنيف تفتح التصنيف؛ لا تفترض أنه خدمة مباشرة لأن اسمه يشبه اسم خدمة.
7. عند الفراغ أو عدم التغطية اعرض رسالة مناسبة ومدخل تغيير الموقع، لا شبكة وهمية ولا spinner دائمًا.
8. للعميل العائد، يمكن إظهار إعادة الحجز/الحجز القادم فقط إذا كانت بياناته ووظيفته الحالية متاحة؛ لا تضف طلب API جديدًا لهذا الغرض.
9. انقل المحتوى الثانوي المتكرر إلى وجهات واضحة. إخفاء قسم من الرئيسية لا يعني حذف endpoint أو Controller تستعمله شاشة أخرى.
10. يجب أن تظهر بداية شبكة الخدمات على هاتف مرجعي بارتفاع منطقي يقارب 800، عند حجم خط 1.0 وبعد اكتمال التحميل. لا يُفرض هذا على خط 2.0 أو شاشة قصيرة بالقوة.

**نموذج الشركة:** لا تعرض الرئيسية كمتجر مزودين مستقلين أو «انضم كمزود». بيانات الفرع تبقى حيث تؤثر في التغطية والحجز، بصيغة NIRAB المناسبة. لا تحذف تدفقات اختيار/تأكيد الفرع المستخدمة وظيفيًا ولا تتجاوزها؛ تبسيطها البصري لا يغيّر قواعدها.

## 4.2 التنقل والسلة والحساب

الوجهات المرئية على الهاتف: **الرئيسية — حجوزاتي — الباقات — حسابي**. يُعرض الترتيب وفق اتجاه اللغة، وتبقى الأيقونات والتسميات متوافقة معه. التمييز ليس باللون وحده؛ استخدم حالة أيقونة ومؤشر/وزن مناسبًا.

السلة تبقى عبر مسارها الحالي ومدخل علوي واضح في الرئيسية وصفحات التصفح. يعرض العداد حالة السلة الحالية، ولا ينشئ Controller آخر. عند وجود عناصر يمكن إظهار «متابعة الطلب»، لكن لا تجمع شريطًا عائمًا للسلة وزر خدمة وشريط تنقل فوق بعضها. في تفاصيل الخدمة الأولوية لشريط الخدمة، وفي السلة للدفع، مع وصول السلة من الرأس.

«حسابي» هو صفحة تجميع واضحة، وليس نسخ `MenuScreen` السفلي داخل Scaffold متداخل. افصل محتوى الحساب عن غلاف عرضه بحيث يمكن استعماله في صفحة رئيسية أو مسار مستقل دون AppBar أو BottomBar مزدوجين.

احتفظ بمداخل الملف الشخصي، العناوين، طلبات عروض الأسعار، الإشعارات، الرسائل، الجودة والدعم، اللغة والمظهر، السياسات، والوظائف المشروطة القائمة مثل المحفظة والنقاط والمفضلة والعروض. لا تُفعّل ميزة عطلتها الإعدادات.

## 4.3 التصفح والبحث والتصنيفات

استعمل التصميم نفسه للبطاقات والفلاتر في نتائج البحث والتصنيف والخدمات والمفضلة. لا تترك نتائج البحث ببطاقات القالب القديمة بينما تتغير الرئيسية.

الحالات المطلوبة: تحميل أولي، قائمة قصيرة/طويلة، تحميل صفحة إضافية، لا نتائج، خطأ شبكة، خدمة غير متاحة، اسم طويل، صورة تالفة. حافظ على pagination والاستعلام والفلاتر الحالية وإمكانية الرجوع إلى موضع القائمة.

## 4.4 تفاصيل الخدمة — قالب واحد بنوعين

**الترتيب المعتمد:** رجوع ومشاركة ومفضلة عند دعمها → اسم ووصف مختصر → معلومة التسعير والمدة الموثوقة إن توفرت → معرض الصور → الوصف/نطاق الخدمة → معلومات إضافية موثوقة → أسئلة شائعة → تقييمات حقيقية → إجراء أساسي متاح.

يمكن توسيط عنوان قصير، لكن الفقرات الطويلة تحاذى لبداية السطر. لا تكرر اسم الخدمة فوق غلاف معتم ثم في بطاقة أخرى. لا تضع الوصف كله في صندوق ضخم متصل دون فواصل.

**الخدمة المسعّرة:** اعرض أساس السعر الصحيح، ولفظ «يبدأ من» فقط عندما يستند إلى أدنى خيار صالح وفق المنطق الحالي. قبل اكتمال الخيارات، الزر «حدد تفاصيل الخدمة». داخل اختيار التفاصيل تُستخدم تسمية «أضف إلى السلة» أو «متابعة الحجز» فقط حين يطابقها الفعل الفعلي.

**خدمة عرض السعر:** اعرض «يُحدد السعر بعد مراجعة تفاصيل الطلب»، أو النص المعتمد المتاح، مع زر «اطلب عرض سعر». لا تعرض صفرًا بوصفه السعر، ولا تضف الخدمة إلى سلة الخدمات المسعّرة، ولا تَعِد بمعاينة مجانية.

**الصور:** استخدم `galleryImages` ثم الغلاف/الصورة المصغرة كبدائل. احذف التكرارات في طبقة العرض دون تعديل البيانات المخزنة. صورة واحدة دون نقاط تنقل، وغياب الصور دون مساحة فارغة كبيرة.

**نطاق الخدمة:** استخدم البيانات المتاحة كما هي. لا تستخرج «يشمل/لا يشمل» بقواعد Regex من HTML، ولا تفترض وجود حقول منظمة غير موجودة. عند عدم وجودها، استخدم عنوان «عن الخدمة» والوصف الغني الموجود؛ لا تُظهر عنوان «تشمل الخدمة» فوق فقرة لا تدعم ذلك.

شريط الإجراء يحجز مساحة فعلية داخل التخطيط، مع مالك واحد لـSafeArea وkeyboard insets حتى لا تتضاعف الهوامش. عند التركيز على حقل يجب أن يبقى الحقل وإجراءه مرئيين؛ وفي الويب لا يحجب العنصر الثابت موضع التركيز [T09]، [T12].

**الأسئلة والتقييمات:** اعرض الموجود فعلًا، مع تعداد صحيح. لا تنشئ تقييمات أو أسماء أو أرقام طلبات وهمية. حافظ على مشاركة رابط الخدمة والمفضلة وإمكانية الوصول من رابط مباشر.

## 4.5 اختيار تفاصيل الخدمة وطلب عرض السعر

أعد تنسيق `ServiceCenterDialog` الحالي، ولا تنشئ رحلة تسعير مستقلة تنافسه. يجب أن تبقى الخيارات والكميات والحقول الديناميكية والحد الأدنى والسعر والفرع وسلوك الإضافة مرتبطة بالمنطق الحالي.

في عرض السعر، أعد تنسيق `CreatePostScreen` وحقوله الديناميكية. احتفظ بمعرّف/slug الخدمة عبر تسجيل الدخول، وأظهر متطلبات الحقول وأخطاءها قربها. حافظ على الحقول والملفات المطلوبة الحالية دون ابتكار حقول إجبارية جديدة.

لا تحوّل `executionType` وعدد الفنيين إلى منتج جديد يختاره العميل من عندك؛ اعرض ما يتيحه التدفق الفعلي فقط، دون تعديل تكليف الفريق أو عدد الموظفين.

## 4.6 السلة وإتمام الطلب

السلة: بطاقة خدمة واضحة، خيارات وكمية، تعديل وحذف مع التأكيد المناسب، وملخص تكلفة. لا تثبّت أسعارًا أو ضرائب داخل Widget. أحكام الفرع/التغطية والحد الأدنى والكوبون والمحفظة محفوظة.

إتمام الطلب يحافظ على الحالات الحالية `orderDetails` و`payment` و`complete`. نظّم اختيار العنوان والموعد والملاحظات داخل الحالة الحالية؛ لا تضف حالات Controller أو تغيّر توقيت إنشاء الحجز لمجرد تقسيم الشاشة.

تظهر أوقات الحجز من مصدر الإتاحة الحالي، لا من قائمة أوقات مصطنعة. أي تغيير للموقع أو الخدمة يعيد التحقق كما يفعل النظام الحالي. الانتقال للخلف لا يمحو إدخالات العميل بلا سبب، ولا يعيد بدء الدفع.

عرض تكلفة واضح قبل التأكيد: البنود التي يرجعها النظام، الخصومات، الضرائب/الرسوم عند وجودها، إجمالي مستحق، وأثر المحفظة. لا تتغير القيمة بالتنسيق ولا تُعرض قيمة تقديرية بوصفها نهائية.

زر الإجراء محمي من التكرار بالحالة الموجودة، ويظهر تحميلًا مناسبًا. النجاح يُعرض بناءً على استجابة النظام وحالته، لا بمجرد العودة من WebView أو بوابة الدفع. لا تنشئ أي محاكاة نجاح في production.

## 4.7 الحساب والحجوزات والباقات

| الحالة | العرض المطلوب |
|---|---|
| حساب الضيف | رسالة ترحيب ودخول، مع اللغة والدعم والسياسات العامة |
| حجوزات الضيف | رسالة مخصصة، وإبقاء تتبع حجز الضيف إذا كان `guestCheckout` يسمح |

باقات الزيارات الحالية ليست شاشة `subscription`/Pro نفسها. أبقِ كل منهما وفق إعداداته ومساراته؛ لا تدمجهما تحت افتراض مالي واحد. شراء الباقة الحالي يعرض سياسة الدفع من المحفظة ويحافظ على `idempotency_key`؛ لا تستبدله بدفع جديد ولا تزل تأكيد الشراء.

عند تسجيل الخروج/تبديل الحساب يجب ألا تبقى بيانات الباقات والحجوزات والحساب السابق في تبويب محفوظ أو ذاكرة شاشة ظاهرة.

## 4.8 الويب وiOS

الويب: محتوى محدود العرض، رأس وتنقل مناسب للشاشة الواسعة، وفي تفاصيل الخدمة/الدفع يمكن وجود محتوى رئيسي وملخص جانبي عندما يسمح عرضهما بذلك. اللوحة الجانبية لا تحجب Footer أو نهاية المحتوى. احتفظ بالتنقل والروابط المباشرة وتحديث الصفحة واللغة المخزنة.

لا تعالج واجهات Flutter الداخلية بتغيير `web/style.css` فقط؛ هذا جزء من غلاف التحميل. حافظ على عمل `brand_bootstrap.js` وإزالة شاشة التحميل عند أول إطار، ولا تُخرج أدوات المعاينة إلى production.

iOS: تغييرات العرض مشتركة، لكن اختبار Android لا يثبت أن iOS بُني أو اختُبر. يلزم macOS/Xcode لبناء iOS؛ ومعه iPhone حقيقي للاختبار، دون Simulator [T06]. عند غياب البيئة يسجل وضع iOS بوضوح، ولا يعاد إنشاء مجلداته أو تعديل توقيعه من Windows.

# 5. قيود المصدر التي تمنع التراجع الوظيفي

## 5.1 التوجيه القديم لا يساوي ترتيب الشريط الجديد

المصدر الحالي يحتوي:

- `BnbItem { homePage, bookings, cart, offers, more }` في `bottom_nav_controller.dart`.
- `getMainRoute(page)` يمرر اسم الصفحة عبر query parameter.
- `RouteHelper` يحول `home / booking / cart / order / menu` إلى أرقام `0 / 1 / 2 / 3 / 4`.
- `BottomNavScreen.initState` يفسر 2 كسلة و3 كعروض؛ لا يجوز تحويلهما صامتًا إلى باقات وحساب لمجرد تغيير الشريط.
- `_bottomNavigationView` في المصدر الحالي يتضمن فرع سلة يعيد `Get.toNamed` من سياق بناء الواجهة، وبعض فروع الضيف قد لا تعيد Widget واضحًا. لا تعِد إنتاج ذلك في الهيكل الجديد.

**العقد المطلوب:** افصل ترتيب الوجهات المرئية عن تفسير المسارات القديمة. يمكن توسيع enum الحالي بأسماء دلالية للباقات والحساب مع إبقاء قيمه القديمة للتوافق، أو إضافة resolver واضح، لكن لا تنشئ مصدرين متنافسين لحالة التبويب.

| المدخل | الوجهة التي يجب الحفاظ عليها/تحديدها صراحة |
|---|---|
| `/home?page=home` | الرئيسية |
| `/home?page=booking` | الحجوزات أو حالة الضيف/التتبع المسموحة |
| `/home?page=cart` | مسار السلة الحالي وحمايته، لا الباقات |
| `/home?page=order` | توافق العروض كما يفسرها المصدر الحالي؛ لا تفترض أنه «حالة نجاح طلب» |
| `/home?page=menu` | يعالج صراحة إلى صفحة الحساب/القائمة المناسبة؛ يوثق إصلاح سقوطه الافتراضي إن كان قائمًا محليًا |
| `/cart` | السلة نفسها، مع السماح الحالي للضيف/المستخدم حسب حمايتها الفعلية |
| `/offers` | العروض، ولو لم تعد في شريط الهاتف |
| `/profile` | الملف الشخصي المحفوظ، لا إعادة توجيه تفقد وظائفه |
| `/visit-packages` | الباقات المحمية؛ تتطابق وظيفيًا مع محتوى تبويب الباقات للمستخدم المسجل |
| روابط الخدمة والحجز والدفع | تبقى بمعاملاتها الحالية؛ لا إعادة تعيينها إلى الرئيسية بعد الدخول |

استخدم المولدات الحالية للروابط، وحافظ على ترميز `redirect_to` وparameters. لا توسّع المدخلات المسموحة ولا تمرر URL خارجيًا جديدًا كوجهة دخول. لا تفترض أن اسم `RedirectRouteValidator` يغني عن مراجعة طريقة استعماله.

كل بناء لجسم الشاشة يعيد `Widget` محددًا. الانتقال الملاحي يحدث في callback أو معالجة دخول مسار محكومة لمرة واحدة، لا `Get.toNamed` داخل `build`. اختبر كل مدخل قديم واستخدم lookup بالاسم لا `enum.index` لتفسير الروابط.

## 5.2 حماية الباقات والحساب عند تضمينهما داخل التبويبات

`/visit-packages` محمي حاليًا بـ`AuthMiddleware`. لكن تضمين `VisitPackagesScreen` مباشرة داخل جسم تبويب لا يمر تلقائيًا عبر middleware الخاص بمسار GetPage.

لذلك يجب فحص حالة الدخول **قبل إنشاء محتوى الباقات المحمي**. لا تنشئ جميع الصفحات مسبقًا داخل `IndexedStack` أو `Offstage` للضيف، لأن `initState` لصفحة الباقات يستدعي جلب البيانات حتى لو كانت مخفية.

احفظ حماية المسارات المباشرة، وأضف حراسة عرض مكافئة لمداخل التبويب، دون حذف middleware أو فتح endpoints. عند logout تخلص من المحتوى المحمي المحفوظ، وعند الدخول أعد تحميل بيانات الحساب الصحيح. لا تُعرض معلومات باقات خاصة في preview عامًا أو حساب ضيف.

## 5.3 مدخل الخدمة واحد

`lib/helper/service_action_helper.dart` يوجّه `pricingType == 'quote'` إلى طلب عرض السعر، مع الدخول والعودة عند الحاجة. أما الخدمة الأخرى فتفتح `ServiceCenterDialog`.

يجب أن يبقى هذا القرار واحدًا في الرئيسية والبحث والمفضلة والتفاصيل. إعادة تنسيق الزر لا تعني نسخ منطق التسعير إلى أربعة ملفات. يمكن توحيد تسمية الإجراء في helper عرض خالص؛ لا تكرر إنشاء الطلب أو الاستدعاء الشبكي.

## 5.4 البيانات المعروفة والبيانات غير المثبتة

| المحتوى | المصدر الحالي | القاعدة |
|---|---|---|
| أسماء وصور التصنيفات | `CategoryModel.name / imageFullPath / slug` | بيانات حقيقية؛ لا IDs أو ترتيب منافس ثابت |
| الوصف المختصر والتفصيلي | `Service.shortDescription / description` | يحافظ على المعنى؛ لا نسخ وصف خدمة إلى غيرها |
| معرض الصور | `Service.galleryImages` من `gallery_image_urls` | قائمة قد تكون فارغة |
| الأسئلة | `Service.faqs` | إخفاء القسم إن لم توجد أسئلة |
| التسعير | `pricingType` والخيارات وبيانات السلة الحالية | لا اختراع مبلغ أو استنتاج النوع من اسم الخدمة |
| مدة الخدمة | `estimatedDurationMinutes` | النموذج يضع 60 افتراضيًا عند غياب المصدر؛ لا تقدمه كمدة مؤكدة |
| نوع التنفيذ/الفريق | `executionType / defaultTechnicians / activeFields` | لا تغيير سياسة التنفيذ والتكليف |
| «يشمل / لا يشمل» منظم | غير مثبت كحقول مستقلة في نموذج Service المفحوص | استخدم الوصف، وسجل احتياج محتوى منفصلًا |
| «لماذا تختارنا»/الضمان | ليس مثبتًا كقائمة خدمة مستقلة | محتوى معتمد فقط؛ وإلا لا يظهر القسم |
| بانر نصي منفصل | يراجع نموذج البانر الحالي أولًا | لا تفترض حقول عنوان/وصف/CTA غير موجودة |

قبل عرض مدة أو سعر كبطاقة ثقة، تحقق من وجود بيانات حقيقية. عند عدم القدرة على تمييز قيمة افتراضية من قيمة واردة لا تعرض المعلومة الجديدة بوصفها حقيقة مؤكدة. لا تعدّل defaults عامة في الموديل لإكمال التصميم دون مراجعة الأثر.

أي نقص يحتاج Backend أو CMS يوثَّق في جدول: الحقل المطلوب، سبب الحاجة، البديل المستخدم الآن، وصاحب القرار. لا توسع هذه المهمة إلى migrations. نقص المحتوى الاختياري لا يمنع استكمال قالب جيد وصادق.

## 5.5 المكوّنات الشبكية وحالة الصفحة

لا تنقل تحميل البيانات إلى `build`، ولا تنشئ `Get.put` جديدًا مع كل rebuild. حافظ على Bindings وControllers الحالية وحالات التحميل والإلغاء والتخلص من Scroll/Animation Controllers.

راجع `HomeScreen.loadData` وRefresh قبل حذف أي استدعاء بسبب إزالة قسم مرئي. يمكن ترشيد استدعاء غير مستخدم فقط بعد التأكد من عدم اعتماد حالة أخرى عليه؛ لا يجعل التغيير البصري خدمات المنطقة أو السلة قديمة.

لا تفعّل تحميلًا لجميع التبويبات الخاصة مقدمًا. استخدم بناءً كسولًا مع حماية مناسبة، واحفظ حالة القوائم دون تسرب معلومات حساب آخر.

## 5.6 مفاتيح الإعداد والترجمة

احتفظ بمفاتيح التخزين واللغة والثيم والمصادقة الحالية، وأضف مفاتيح نصوص جديدة بنطاق واضح مثل `rui_*` في ملفات العربية والإنجليزية. لا تستبدل ملف اللغة كاملًا، ولا تحذف المفاتيح أو اللغات القائمة.

مصطلحات الواجهة: «الفرع» بدل مزود مستقل، و«الفني/فريق العمل» عند عرض موظفي NIRAB، و«طلب عرض سعر» بدل لغة سوق العطاءات حيث تسمح دلالة التدفق. هذا تغيير نصي، لا تغيير لأسماء حقول API أو قيم الحالات في الخلفية.

# 6. الجرد قبل التنفيذ — لا صفحة منسية ولا وظيفة مفقودة

أنشئ جدولًا فعليًا من `RouteHelper` ووجهات القوائم والمكونات المفتوحة بالـdialog/bottom sheet. لا تعتمد على الصور المرفقة وحدها، لأنها لا تغطي كل التطبيق.

| مجموعة الواجهات | نطاق المعالجة |
|---|---|
| الرئيسية/التنقل | إعادة تنظيم كاملة وفق المواصفة |
| التصنيفات/الخدمات/البحث/المفضلة/العروض | قالب قوائم وبطاقات موحد مع وظائفها الحالية |
| تفاصيل الخدمة/اختيار الخيارات | إعادة تصميم كاملة مع حفظ المدخل الوظيفي |
| طلب عرض السعر/قائمة الطلبات/تفاصيل العرض | إعادة تنسيق وربط بصري دون تغيير قبول/رفض العرض |
| السلة/Checkout/الدفع/النجاح والفشل | إعادة تنظيم العرض دون تغيير حالات العملية |
| الحجوزات/التفاصيل/التتبع/إعادة الحجز | توحيد البطاقات والتفاصيل والإجراءات |
| الباقات/حجز زيارة/السجل | إعادة تنسيق مع حماية الدخول وسياسة المحفظة القائمة |
| الحساب/التعديل/العناوين/الإعدادات | صفحة حساب واضحة، ونماذج وحالات موحدة |
| الدخول/التسجيل/OTP/استعادة الحساب/الدخول الاجتماعي | هوية موحدة دون تغيير سياسات أو إعدادات مقدمي المصادقة |
| المحادثات/الإشعارات/مركز الجودة/الدعم | مواءمة مكونات العرض، مع بقاء الوظائف والمرفقات |
| المحفظة/النقاط/الإحالة/القسائم/Pro | مواءمة عند تفعيلها، دون تفعيل أو تغيير منطق مالي |
| الموقع/الخرائط/تغطية الخدمة | إعادة تنسيق الأغلفة والحقول فقط؛ لا استبدال خرائط أو مفاتيح |
| صفحات HTML/السياسات/عن الشركة | تحسين القراءة والاتجاه والعناوين دون تحرير الالتزامات التجارية |
| Onboarding/Splash/عدم التوفر/الصيانة/التحديث/الخطأ | هوية وحالات متسقة؛ لا تعطيل بوابات الصيانة أو التحديث |
| Web landing إن كانت مستقلة | مواءمة الهوية المشتركة ومراجعة الرابط؛ لا استبدال صفحة إنتاج أخرى خارج المستودع |

يسجل لكل وجهة: المسار أو مدخل الفتح، ملف الشاشة، حالتها للضيف/المسجل، الـfeature flag، المكونات المستخدمة، المرحلة، وحالة التحقق. ميزة غير مفعلة يمكن وسمها `NOT_APPLICABLE` فقط مع بيان الإعداد، لا لأنها لم تُراجع.

الجرد لا يعني إعادة كتابة كل ملف. المطلوب تغطية الواجهات القابلة للوصول؛ المكونات الداخلية التي تتحدث عن Providers قد تبقى بأسمائها البرمجية مع مصطلحات عميل صحيحة.

# 7. مراحل التنفيذ وبوابات القبول

## RUI-01 — خط الأساس ونقطة الاعتماد

**الغرض:** منع تنفيذ تصور خاطئ على نطاق واسع، وإثبات أن بيئة المستخدم والهاتف صالحان للاختبار قبل تغيير التطبيق.

### الأعمال بالترتيب

1. اقرأ تعليمات المستودع المحلية إن وجدت، وسجل HEAD والفرع والتغييرات السابقة.
2. قارن خريطة المصدر في الملحق مع الملفات المحلية. تحقّق من وجود `android/` و`ios/` محليًا؛ غيابهما عن أرشيف المراجعة ليس سببًا لتوليدهما من جديد.
3. سجل SDK من `flutter --version` والاعتماديات المقفلة. ملف Dockerfile في الأرشيف يشير إلى Flutter 3.44.0، و`pubspec.yaml` يطلب Dart `^3.9.2`؛ لا تستنتج نسخة اللابتوب منهما ولا ترقِّها تلقائيًا.
4. تحقق من الهاتف وفق القسم 8، ثم شغّل `lib/main.dart` قبل التعديل. سجل عوائق baseline منفصلة عن أخطاء إعادة التصميم.
5. التقط خط أساس مختصر للرئيسية، خدمة مسعّرة، خدمة عرض سعر، والتنقل/السلة أو Checkout إن سمحت بيانات الاختبار. لا تنشئ حجزًا أو دفعًا لهذا الغرض.
6. أنشئ جرد الشاشات ومصفوفة المدخل القديم → الوجهة الجديدة، وقائمة مخاطر auth/cart/quote/package/checkout.
7. جهّز المكونات الأولى والتصورات الثلاثة باتجاه واحد. يمكن إنشاء نقطة تشغيل معاينة تحت `tools/` تستخدم مكونات العرض نفسها مع بيانات fixtures واضحة إذا كانت بيانات API غير متاحة.
8. شغّل المعاينة على الهاتف الحقيقي أيضًا، وصنّف صورها `PREVIEW/FIXTURE`، لا `REAL_APP/API`. لا تُدخل fixtures في `lib/main.dart` أو بدائل repository للإنتاج.
9. اعرض الصور والمقاسات والسلوك المقترح في `DESIGN_LOCK.md`، وسجل اعتماد المستخدم أو ملاحظته الموحدة. لا تعمم الصفحة غير المعتمدة.

### بوابة القبول G1

- [ ] الفرع وخط الأساس معروفان، وعمل المستخدم محفوظ.
- [ ] اكتشاف الهاتف الحقيقي وتشغيل التطبيق الأساسي موثقان، أو يوجد blocker صريح يمنع بوابة الاختبار.
- [ ] القرارات الثلاثة البصرية معروضة ومصدر كل لقطة واضح.
- [ ] اعتماد بصري واحد مسجل قبل التعميم.
- [ ] التعديلات الأولية قابلة لإعادة الاستخدام، لا نموذج منفصل سيُرمى وتُكتب الشاشات من جديد.

**حد المرحلة:** لا API جديدة، لا ترقية حزم، ولا بناء كامل لكل الشاشات قبل الاعتماد. يمكن استكمال الجرد والفحوص الساكنة أثناء انتظار الاعتماد، لا التعميم.

## RUI-02 — تثبيت نظام التصميم

**الغرض:** مصدر واحد للتنسيق قبل نقل الصفحات إليه.

### الأعمال

1. طبق القيم المعتمدة في BrandTokens والثيمين وأنماط النص، وراجع أثر المقاسات الجديدة على المكونات المشتركة.
2. وحّد الأزرار الرئيسية والثانوية والحقول والقوائم وDialogs/Snackbars وحالات التعطيل والتحميل والتركيز.
3. أكمل المكونات العامة في القسم 3.4، واستخرج مكوّن عرض الضيف من غلافه لتفادي ازدواج AppBar/Scaffold.
4. أضف ترجمات العربية والإنجليزية دون المساس بمفاتيح التخزين أو اللغات الأخرى.
5. أضف اختبارات صغيرة للزر، وبطاقة التصنيف طويلة الاسم، وحالة الضيف، وشريط الإجراء مع نص مكبر واتجاهين.
6. افحص الثيم الداكن في نفس المكونات. لا تؤجل جميع مشاكله إلى النهاية أو تجبر التطبيق على Light.
7. عاين المكونات على الهاتف، واستخدم Hot Reload عندما يكون مناسبًا بدل إعادة تنزيل الاعتماديات والبناء في كل تغيير.

### بوابة القبول G2

- [ ] مكون عام واحد لكل مسؤولية متكررة، ولا كتل تنسيق متعارضة.
- [ ] النص والتفاعل يظلان قابلين للاستخدام عند 1.0 و1.3 و2.0.
- [ ] لا overflow في مكونات الأساس ضمن مقاسات الاختبار.
- [ ] التباين وحالات Focus/Disabled/Loading موثقة، والاختبارات الصغيرة ذات الصلة ناجحة.

## RUI-03 — الرئيسية والتنقل والتصفح

**الغرض:** تحقيق أول تجربة واضحة للعميل وربط الوجهات الجديدة دون كسر الروابط السابقة.

### الأعمال

1. أعد تركيب `HomeScreen` و`WebHomeScreen` بالمكونات المشتركة مع إبقاء تحميل المنطقة والإعدادات وتجديد البيانات صحيحًا.
2. نفّذ شبكة التصنيفات، ومعالجة البانر والصور الفارغة، والبحث ومحتوى العميل السياقي المتاح.
3. نفّذ الشريط الرباعي ومدخل السلة ووجهات العروض والحساب، من دون ظهور شريطين سفليين في الصفحة نفسها.
4. طبق resolver/خريطة التوافق في القسم 5.1. امسح استدعاءات `getMainRoute` و`BnbItem` و`pageIndex` قبل إنهاء التغيير.
5. أضف حماية التبويبات الخاصة قبل إنشائها. لا تعتمد على middleware المسار وحده.
6. حافظ على تتبع حجز الضيف وفق الإعداد الحالي، وعلى عودة الدخول إلى الوجهة المقصودة.
7. طبّق بطاقات القوائم على التصنيفات والبحث والمفضلة والعروض، مع حفظ pagination والاختيارات.
8. اختبر تغيير اللغة والتبويب وعرض المتصفح والدخول والخروج دون صفحات فارغة أو قفزات ملاحة متكررة.

### بوابة القبول G3

- [ ] ترتيب الرئيسية مقارب للمواصفة المعتمدة، وخدمات NIRAB الفعلية تظهر دون تثبيت بيانات المنافس.
- [ ] كل وجهة قديمة في جدول التوافق تعمل بما يقابلها الصحيح.
- [ ] مدخل السلة واضح، والعداد مرتبط بالبيانات الفعلية، ولا ضياع لوظائف العروض/القائمة السابقة.
- [ ] فتح تبويب الباقات للضيف لا ينشئ الصفحة المحمية ولا يطلب بيانات حساب.
- [ ] جسم كل تبويب Widget صحيح، ولا navigation أو طلب API متكرر من `build`.

## RUI-04 — تفاصيل الخدمة ومسارا التسعير

**الغرض:** صفحة خدمة مكتملة بصريًا ومرتبطة بالفعل الصحيح.

### الأعمال

1. أعد تركيب `ServiceDetailsScreen` حول القالب المعتمد بدل الغلاف المعتم والبطاقة المتداخلة والتبويبات غير الضرورية.
2. احتفظ بكل البيانات والوظائف القائمة: المفضلة، المشاركة، الوصف، المعرض، الأسئلة، التقييمات، والسعر/الخيارات.
3. اربط CTA بـ`ServiceActionHelper`؛ لا تكرر منطق التفرع أو تنقل quote إلى cart.
4. أعد تنسيق `ServiceCenterDialog` للخيارات والكميات والحقول الحالية؛ راجع لوحة المفاتيح والتمرير وارتفاع bottom sheet.
5. أعد تنسيق `CreatePostScreen` ومكوناته، مع بقاء الخدمة المختارة بعد auth redirect والحقول والملفات المطلوبة كما هي.
6. عالج البيانات الجزئية بصدق: صور/أسئلة مفقودة، عنوان طويل، وصف HTML طويل، سعر غير متاح، مدة افتراضية، خدمة غير متاحة.
7. سجل الفجوات التي تحتاج محتوى من الإدارة بدل ملئها بوعود منافس أو حقول backend وهمية.
8. اختبر مداخل تفاصيل الخدمة من الرئيسية والبحث والتصنيف والمفضلة والرابط المباشر؛ يجب أن تنتهي جميعها إلى نفس قرار الطلب.

### بوابة القبول G4

- [ ] الخدمة المسعّرة تعرض أساس السعر وتفتح الخيارات/السلة الصحيحة.
- [ ] عرض السعر يفتح طلب العرض مع الخدمة الصحيحة ولا يُضاف إلى سلة مسعّرة.
- [ ] السعر والمدة والوصف لا يقدمون معلومات مخترعة أو التزامات غير معتمدة.
- [ ] شريط الإجراء لا يغطي آخر فقرة أو سؤال أو تحكم عند تكبير الخط وفتح لوحة المفاتيح.
- [ ] النوعان مختبران على الهاتف الحقيقي؛ ما لم يتوفر من بيانات حقيقية يُعلَّم Blocked لا Passed.

## RUI-05 — رحلة الطلب والحساب والمتابعة

**الغرض:** عدم ترك الرحلة تتغير فجأة بعد الضغط على زر الحجز.

### الأعمال بالتتابع

1. **السلة:** بطاقات الخدمة والخيارات والكميات والفرع وملخص التكلفة والكوبون، مع الحفاظ على طريقة التحديث الحالية.
2. **تفاصيل الطلب:** العنوان والموعد والملاحظات والحجز المتكرر عندما يكون متاحًا، ضمن حالات Checkout الحالية دون state machine جديد.
3. **الدفع:** تنسيق وسائل الدفع المفعلة فقط، والمبالغ وشروط التأكيد وحالات الإلغاء/الفشل/العودة، دون تغيير معالجة session/token.
4. **النتيجة:** رسالة ومعلومات مرجع الطلب مبنية على استجابة حقيقية؛ لا إظهار نجاح تجميلي.
5. **الحجوزات:** القائمة والتفاصيل والتتبع وإعادة الحجز والفواتير والإثباتات والتواصل، مع إظهار الإجراءات المسموح بها فقط.
6. **عروض الأسعار:** قائمة الطلبات والتفاصيل والعروض وقبولها/متابعتها ضمن التدفق الحالي؛ لا إعادة تقديمها كسوق مزودين مستقلين.
7. **الباقات:** الباقات والخطط والزيارات والسجل والتجديد/السياسات الحالية، مع حفظ الحماية وتأكيد المحفظة وidempotency.
8. **الحساب والمصادقة:** صفحة الحساب، تعديل الملف، العناوين، الدخول والتسجيل وOTP والاستعادة وGoogle/Apple بحسب الإعداد والمنصة الحالية، دون تهيئة مفاتيح جديدة.
9. **الشاشات الثانوية:** طبّق نظام التصميم على بقية الجرد في القسم 6؛ لا تُنشئ وظائف غير موجودة لسد فراغ بصري.
10. **التدقيق الوظيفي:** قارن روابط الإجراءات، payloads ذات الصلة، وحالات Controllers قبل/بعد. أي تغيير سلوكي ضروري يوثق منفصلًا عن إعادة التنسيق.

### بوابة القبول G5

# 8. بروتوكول اختبار الهاتف الحقيقي — شرط إلزامي

## 8.1 ما يُعد اختبارًا مقبولًا

يجب تشغيل **التطبيق الفعلي من `lib/main.dart`** على الهاتف الحقيقي المتصل باللابتوب، ثم التفاعل مع الشاشات والتحقق من نتائج الإجراءات المسموحة. بناء APK أو مشاهدة Preview أو نجاح `flutter analyze` لا يثبت نجاح الاختبار الفعلي.

أوضح المستخدم أن التطبيق لا يعمل لديه على المحاكي وأن اختباره يتم على الهاتف الحقيقي. هذا قيد تنفيذ لهذه المهمة، وليس ادعاءً عامًا بأن Flutter لا يدعم المحاكيات.

إذا كانت أدوات الوكيل لا تتيح الضغط داخل التطبيق، تُجرى الخطوات بمساعدة المستخدم على الهاتف نفسه، وتوثق النتائج المشاهدة. لا يدّعي الوكيل أنه نفذ تفاعلًا لم ينفذه أو لم يشاهد دليله.

## 8.2 التحضير

اعمل من جذر المستودع المحلي الكامل. افتح قفل الهاتف وفعّل USB debugging ووافق على رسالة تفويض الكمبيوتر عند ظهورها. لا تتجاوز التفويض أو تغيّر خيارات أمان الجهاز. تدعم وثائق Flutter وAndroid هذا المسار للتحقق من الاتصال والتشغيل [T01]، [T02].

إذا تعذر اتصال الجهاز، عالج الكابل/وضع USB/التفويض/تعريف الجهاز المناسب. لا تُنزل emulator كبديل. لا تنفذ `adb kill-server` تلقائيًا إذا كان قد يقطع جلسات أخرى؛ يُطلب ذلك فقط عند تشخيص واضح وموافقة المستخدم.

## 8.3 اكتشاف الأدوات والجهاز في PowerShell

الكتلة التالية مخصصة لبيئة Windows المحلية، وليست لأداة تعمل داخل حاوية بعيدة لا تتصل بهاتف المستخدم. لا تضع Serial افتراضيًا أو من صورة قديمة.

```powershell
# Run from the full local user-app-web repository.
$ErrorActionPreference = 'Stop'
if (-not (Test-Path '.\pubspec.yaml')) {
    throw 'Run this from the Flutter project root.'
}
if (-not (Test-Path '.\android')) {
    throw 'The local native Android project is missing. Do not regenerate it.'
}

Get-Command flutter -ErrorAction Stop | Out-Null
flutter --version
if ($LASTEXITCODE -ne 0) { throw 'Flutter is unavailable.' }
flutter doctor -v
# Review Android/toolchain findings; do not upgrade SDKs automatically.

$adbCommand = Get-Command adb -ErrorAction SilentlyContinue
if ($adbCommand) {
    $Adb = $adbCommand.Source
} else {
    $sdkRoots = @(
        $env:ANDROID_HOME,
        $env:ANDROID_SDK_ROOT,
        (Join-Path $env:LOCALAPPDATA 'Android\Sdk')
    ) | Where-Object { $_ -and (Test-Path $_) }

    $adbCandidates = @($sdkRoots | ForEach-Object {
        Join-Path $_ 'platform-tools\adb.exe'
    } | Where-Object { Test-Path $_ } | Select-Object -Unique)

    if ($adbCandidates.Count -ne 1) {
        throw 'Resolve the adb.exe path from the existing Android SDK; do not guess.'
    }
    $Adb = $adbCandidates[0]

& $Adb devices -l
if ($LASTEXITCODE -ne 0) { throw 'ADB device discovery failed.' }
flutter devices
if ($LASTEXITCODE -ne 0) { throw 'Flutter device discovery failed.' }
```

إذا لم يُكتشف SDK في هذه الأماكن، استخدم مساره المحلي الفعلي من إعدادات Android Studio/المشروع، ولا تُثبت بيئة جديدة عشوائيًا. راجع أسماء الأجهزة الظاهرة مع المستخدم إذا كان أكثر من هاتف متصلًا.

الكتلة التالية تختار جهازًا واحدًا فقط بعد تصفية Android الحقيقي والمصرح له؛ لا تختار Chrome أو Windows أو أول جهاز بلا تحقق:

```powershell
$adbLines = & $Adb devices
if ($LASTEXITCODE -ne 0) { throw 'Cannot read ADB devices.' }
$authorizedIds = @($adbLines | ForEach-Object {
    if ($_ -match '^(\S+)\s+device(?:\s|$)') { $Matches[1] }
})

$rawDevices = flutter devices --machine
if ($LASTEXITCODE -ne 0) { throw 'Flutter machine device discovery failed.' }
$flutterDevices = ($rawDevices -join "`n") | ConvertFrom-Json

$realDevices = @($flutterDevices | Where-Object {
    $_.targetPlatform -like 'android*' -and
    $_.emulator -eq $false -and
    $_.id -notlike 'emulator-*' -and
    $authorizedIds -contains $_.id
})

if ($realDevices.Count -eq 0) {
    throw 'No authorized physical Android phone. Stop device testing; no emulator fallback.'
}
if ($realDevices.Count -gt 1) {
    $realDevices | Select-Object name, id, targetPlatform | Format-Table
    throw 'Multiple physical phones: obtain the intended device selection first.'
}

$DeviceId = $realDevices[0].id
$qemu = & $Adb -s $DeviceId shell getprop ro.kernel.qemu
if ($LASTEXITCODE -ne 0) { throw 'Cannot verify the selected device.' }
if (($qemu -join '').Trim() -eq '1') {
    throw 'Emulator detected: this task requires a physical phone.'
}

& $Adb -s $DeviceId get-state
if ($LASTEXITCODE -ne 0) { throw 'The selected phone is not ready.' }
Write-Host ('Selected physical phone: ' + $realDevices[0].name)
```

راجِع مخرجات `--machine` للـSDK المحلي إذا اختلف تركيبها، ولا تُسقط فحص `emulator` لتجاوز خطأ parsing. استخدم معرّف الجهاز المختار نفسه في جميع أوامر `run` و`logs` واللقطات. أخفِ معرّف الجهاز الكامل عند نشر التقارير خارج بيئة العمل.

## 8.4 الاعتماديات والتشغيل

راجع أمر التشغيل المحلي الحالي وملفات IDE/flavors إن وجدت. أمثلة هذه الوثيقة تستخدم `lib/main.dart`؛ أضف فقط وسائط المشروع المطلوبة الموجودة بالفعل. لا تفترض وجود `--dart-define` يغيّر base URL إذا كان المصدر لا يدعمه.

إذا كانت الاعتماديات محلولة وتعمل بالفعل، لا تعِد تنزيلها. عند الحاجة فقط:

```powershell
flutter pub get
if ($LASTEXITCODE -ne 0) { throw 'Dependency resolution failed.' }
git diff -- pubspec.yaml pubspec.lock
```

أي تغيير غير متوقع للقفل يراجع قبل المتابعة. لا تعالج الخطأ بـ`flutter pub upgrade` أو حذف caches.

```powershell
# The application itself, on the confirmed physical phone.
flutter run -d $DeviceId --debug -t lib/main.dart --no-pub
```

استخدم جلسة Flutter واحدة، وHot Reload للتنسيق، وHot Restart عندما تتغير التهيئة أو يلزم تحديث الأصول. عند انتهاء العمل أوقف الجلسة بشكل عادي ثم أعد التشغيل البارد للتحقق، دون uninstall أو مسح بيانات الهاتف.

عند الحاجة لمعاينة معزولة، استخدم target تحت `tools/` وسجله بوضوح في الدليل؛ هذه ليست بديلًا لاختبار `lib/main.dart`.

لجولة السلاسة النهائية فقط، بعد التأكد من إعداد تشغيل Profile المتوافق محليًا:

```powershell
flutter run -d $DeviceId --profile -t lib/main.dart --no-pub
```

لا تنفذ Debug وProfile بالتوازي على التطبيق نفسه، ولا تغيّر التوقيع لحل تعارض تثبيت. أوامر Flutter موثقة في [T05]، وقياس الأداء يراجع في وضع Profile [T10].

## 8.5 اللقطات والأدلة دون مشكلات PowerShell

التقط الشاشة والتطبيق في المقدمة، دون إشعارات أو بيانات شخصية غير لازمة. لا تستخدم إعادة توجيه مخرجات PNG الثنائية بـ`>` في Windows PowerShell القديم. استخدم ملفًا على الجهاز ثم `adb pull` [T13]:

```powershell
$CaptureDir = Join-Path (Get-Location) 'artifacts\rui-local\device'
New-Item -ItemType Directory -Force -Path $CaptureDir | Out-Null
$CaptureName = 'nirab-rui-' + (Get-Date -Format 'yyyyMMdd-HHmmssfff') + '.png'
$RemoteCapture = '/sdcard/' + $CaptureName

& $Adb -s $DeviceId shell screencap -p $RemoteCapture
if ($LASTEXITCODE -ne 0) { throw 'Device screenshot failed.' }
& $Adb -s $DeviceId pull $RemoteCapture (Join-Path $CaptureDir $CaptureName)
if ($LASTEXITCODE -ne 0) { throw 'Screenshot transfer failed.' }
```

لا تنشر logs خامًا قد تحتوي tokens أو أرقام هواتف أو روابط جلسات دفع. احفظ الأدلة محليًا وشارك نسخة منقحة فقط. لا تدخل `artifacts/rui-local/` إلى commits؛ يمكن إضافته إلى ملف التجاهل المحلي `.git/info/exclude` دون إفساد قواعد موجودة.

## 8.6 مصفوفة عوائق الجهاز

| العائق | التصرف المطلوب |
|---|---|
| `unauthorized` | يفتح المستخدم الهاتف ويوافق على تفويض USB؛ لا تجاوز أمني |
| `offline` أو لا جهاز | فحص الكابل/USB/التعريف/اتصال Flutter؛ لا تشغيل محاكي |
| عدة أجهزة حقيقية | تحديد المقصود صراحة، لا الاختيار العشوائي |
| معرّف `emulator-*` | رفض استخدامه في هذه المهمة |
| غياب `android/` محليًا | طلب نسخة المشروع الأصلية الكاملة؛ ممنوع `flutter create .` |
| تعارض توقيع التطبيق المثبت | توقف، ولا uninstall/clear data ولا تعديل Firebase أو applicationId |
| API غير قابل للوصول | فصل مشكلة الاتصال عن الواجهة؛ لا استخدام عنوان emulator ولا تغيير خادم الإنتاج |
| خطأ الدخول الاجتماعي أو OTP سابق | توثيق baseline/config؛ لا تغيير مفاتيح أو إزالة الحماية |
| الوكيل يعمل في بيئة بعيدة | لا يدّعي اتصال الهاتف؛ ينفّذ صاحب البيئة المحلية جزء الجهاز ويوثق الدليل |
| لا توجد بيانات/بيئة آمنة للدفع | تحقق العرض محليًا، وضع الاختبار التشغيلي Blocked |

لا تعِد الأمر الفاشل مرارًا دون تغيير تشخيصي. احفظ أول رسالة مفيدة، وحدد سبب المنع. يمكن متابعة الشيفرة والفحوص المحلية غير المحجوبة، لكن لا تُغلق قبول الهاتف حتى يُختبر بالفعل.

# 9. الفحوص التقنية والبناء

## 9.1 سياسة التحقق

المطلوب فحوص مركزة، لا تشغيل منظومة Backend أو تحميل بيئة integration ثقيلة. اختبارات Widget تعمل مع harness الاختبار وليست محاكي هاتف، وتُستخدم بجانب اختبار الجهاز الحقيقي لا بدلًا منه [T11].

قارن النتائج بخط الأساس. لا تعِد تنسيق المستودع كله ولا «تصلح» كل lint قديم ضمن مهمة UI. لا تضف suppressions عامة لإخفاء أخطاء جديدة.

## 9.2 عند كل مرحلة

- راجع `git diff --check` وملفات المرحلة فقط.
- نسق ملفات Dart المعدلة/الجديدة باستخدام `dart format` عليها تحديدًا.
- شغّل التحليل للمشروع أو النطاق المناسب، مع مقارنة baseline وعدم تجاهل الأخطاء العابرة بين الملفات.
- شغّل اختبارات المكونات المتأثرة؛ لا تُحدّث توقعاتها لمجرد إسكات فشل وظيفي.
- نفذ مراجعة هاتف مختصرة لما تغير في المرحلة، دون إعادة كامل مصفوفة القبول كل مرة.

```powershell
git diff --check
if ($LASTEXITCODE -ne 0) { throw 'Whitespace/conflict-marker review failed.' }

# Format the explicit list of Dart files changed by this phase.
# Do not run a repository-wide formatting rewrite.
flutter analyze --no-pub
# Record output and exit status, including any pre-existing diagnostics.
```

يُبنى في المرحلة الأولى baseline تشخيصي. بعد ذلك، أي Error جديد أو Warning جديد سببه التعديل يجب علاجه. الملاحظات القديمة خارج النطاق تسجل ولا تنسب إلى التنفيذ الجديد.

## 9.3 الاختبارات الموجودة التي لا ينبغي فقدها

هذه الملفات موجودة في الأرشيف؛ وجودها لا يعني أنها شُغّلت في إعداد هذه الخطة:

```text
test/widget_test.dart
test/theme/brand_theme_test.dart
test/common/widgets/brand_logo_test.dart
test/common/widgets/custom_button_test.dart
test/common/models/config_model_test.dart
test/feature/checkout_progress_test.dart
test/brand_visual_test.dart
```

شغّل الاختبارات السريعة ذات الصلة. راجع `brand_visual_test.dart` قبل تشغيله؛ لا تحدث صور اعتماد/أدلة بصرية آليًا لمجرد اختلافها. إذا فُرضت صورة جديدة بسبب تصميم معتمد، يسجل سبب الاختلاف واعتماده.

أضف تحت `test/rui/` اختبارات صغيرة **جديدة** بحسب المكونات الفعلية. الحد الأدنى يغطي:

| المجموعة | ما تثبته |
|---|---|
| التوجيه | المدخل القديم يصل إلى الوجهة الصحيحة رغم تغيير ترتيب الشريط |
| auth tabs | الضيف لا ينشئ محتوى الباقات المحمي ولا يرسل طلب بياناته |
| service actions | fixed → خيارات، quote → طلب عرض/دخول وعودة؛ لا cart للـquote |
| التكيف | بطاقة اسم طويل وGuestState وActionBar دون overflow في RTL/LTR وتكبير النص |
| حالة الإجراء | loading يمنع إعادة استدعاء callback أثناء العملية؛ لا إنشاء طلب من build |
| البيانات الناقصة | لا صور/لا أسئلة/سعر غير متاح تعطي عرضًا صادقًا بلا crash |
| حفظ البيانات | تغيير التبويب/العرض لا يفقد إدخالًا قائمًا أو يكشف بيانات بعد logout |

لا تضف حزمة اختبار ثقيلة لإكمال هذه البنود. يمكن فصل قرار التنقل/تسمية الإجراء إلى دوال خالصة قابلة للاختبار، أو استخدام mocks صغيرة للعرض، دون تبديل service repositories في التطبيق الفعلي.

## 9.4 فحوص الويب

شغّل الويب في المتصفح المناسب بالأمر المحلي المعتمد، مثل:

```powershell
flutter run -d chrome -t lib/main.dart --no-pub
```

هذا **اختبار ويب**، لا بديل Android. تغيير عرض نافذة المتصفح لا يعادل اختبار هاتف حقيقي، لكنه صالح لمراجعة تكيف نسخة الويب.

البناء النهائي المحلي، بعد مراجعة إعدادات المستودع الحالية:

```powershell
flutter build web --release --base-href=/ --no-pub
if ($LASTEXITCODE -ne 0) { throw 'Web release build failed.' }
```

يتوافق `--base-href=/` مع Dockerfile المفحوص؛ إن اختلف إعداد النشر المحلي المعتمد، يحافَظ عليه ويوثَّق بدل تغييره. لا تشغّل Docker أو Dokploy أو تنشر الناتج ضمن المهمة.

إذا تغير غلاف التحميل أو ملفاته، أو عند فحصه النهائي وكانت Node متاحة، شغّل الاختبار الموجود:

```powershell
node tools/verify_brand_bootstrap.cjs
if ($LASTEXITCODE -ne 0) { throw 'Web appearance bootstrap verification failed.' }
```

لا تثبت Node أو أدوات متصفح ضخمة لمجرد اجتياز خطوة غير متاحة؛ سجل مانع الأداة. لا تصرح بأن guard نجح إذا لم يعمل.

القياسات المنطقية ليست pixels الصورة المرجعية. لا تعتبر لقطة بعرض 702px وصفة لتصميم عرض Flutter قدره 702. استخدم أبعاد التطبيق الفعلية.

## 9.6 قواعد قبول الأداء

استخدم الجهاز نفسه وبيانات وظروفًا متقاربة للمقارنة قبل/بعد. لا تدّعي FPS أو زمن فتح بلا قياس. يرفض أي تراجع واضح مثل تحميل الصفحة كلها عند كل نقرة، زيادة غير مبررة في طلبات API، إعادة جلب جميع الصور عند تبديل تبويب، أو تأخر إدخال النص بسبب إعادة بناء مفرطة.

في جولة Profile مختصرة راجع التمرير وفتح الخيارات وظهور لوحة المفاتيح والتبديل بين التبويبات. أصلح مشاكل الواجهة الناتجة عن التغيير، دون مشروع تحسين أداء خارج النطاق. الأرقام إن قيست تُرفق بظروف القياس، لا بوعود مطلقة.

# 11. سجل التنفيذ والتسليم ومنع إعادة العمل

## 11.1 ملفات التسليم داخل المشروع

لا تُنشئ عشرات تقارير متكررة. استخدم الوثائق التالية تحت `docs/rui/`:

| الملف | المحتوى |
|---|---|
| `NIRAB_CUSTOMER_UI_UX_EXECUTION_PLAN.md` | نسخة هذه المواصفة دون تعديل تاريخي صامت |
| `SCREEN_INVENTORY.md` | جدول الواجهات والمسارات والحماية والمكونات والمرحلة والتحقق |
| `DESIGN_LOCK.md` | المقاسات والقرارات والصور المعتمدة ونقطة اعتماد المستخدم |
| `IMPLEMENTATION_REPORT.md` | تقرير متدرج: baseline، المراحل، الملفات، الفحوص، QA، القيود وقرار التسليم |
| `CONTENT_GAPS.md` عند الحاجة فقط | احتياجات المحتوى/البيانات خارج نطاق UI والبديل الحالي |

الأدلة الخام/الخاصة محليًا تحت `artifacts/rui-local/`. يمكن إدراج صور منقحة في وثائق المشروع فقط بعد التأكد من خلوها من بيانات العملاء والأسرار. المرجع المنافس يبقى في مجلد مراجعة منفصل وغير مسجل في أصول Flutter، ولا يُنشر في مستودع عام دون صلاحية مناسبة.

## 11.2 قالب تقرير كل مرحلة

```markdown
## RUI-0X — اسم المرحلة
الحالة: NOT_STARTED / IN_PROGRESS / READY_FOR_REVIEW / DONE / BLOCKED
الـBase commit:
الـCommit المحلي الخاص بالمرحلة:

### ما تغير
| الملف/المكون | التغيير | أثره الوظيفي إن وجد |
|---|---|---|

### الفحوص الفعلية
| الفحص | الأمر/الخطوات | المنصة/الجهاز | النتيجة | الدليل |
|---|---|---|---|---|

### الفروق عن baseline
- أخطاء سابقة:
- أخطاء جديدة عولجت:
- عوائق متبقية:

### قبول المرحلة
- البنود المجتازة:
- البنود المحجوبة وسببها:
- اعتماد بصري عند RUI-01:
```

لا تملأ النتيجة بكلمة «ناجح» لأن الكود يبدو منطقيًا. Build وStatic Check وPreview وReal Device وOperational E2E أنواع أدلة مختلفة يجب عدم دمجها في عبارة واحدة.

## 11.3 التحكم في التغيير أثناء التنفيذ

بعد DESIGN_LOCK، لا تغير نظام الألوان أو ترتيب الوجهات أو شكل البطاقات من جديد دون سبب موثق. أصلح أخطاء المقاسات/التفاعل وفق نفس النظام بدل إضافة نمط ثالث.

طلب يضيف وظيفة backend أو حقلًا إلزاميًا أو وسيلة دفع أو سياسة جديدة يتحول إلى بند خارج النطاق؛ يوضح البديل الحالي والتأثير، ولا يندمج خفية في commit «UI».

إذا ظهر خلل قديم يمنع العمل: سجله مع خطوات إعادة الإنتاج. يسمح بإصلاح صغير داخل نطاق العميل إذا كان ضروريًا ومفهوم الأثر؛ أما تغيير منطق مالي/أمني أو عقد API فيحتاج تفويضًا منفصلًا. لا تكتفِ بإخفاء الزر الذي يكشف الخطأ.

## 11.4 خطة العودة

احتفظ بمرجع HEAD قبل البداية وcommits صغيرة لكل مرحلة أو جزء مستقل منها. لا تُنشئ flag جديدًا في backend أو نظامي واجهات كاملين للإنتاج لمجرد إمكانية الرجوع.

عند الحاجة إلى العودة مستقبلًا، يراجع صاحب المشروع commits المهمة ويطبق عكسها بترتيب مدروس، لا reset تدميريًا لعمل لاحق. عملية النشر أو الرجوع في الإنتاج ليست ضمن تفويض الوكيل الحالي.

## 11.5 صيغة قرار التسليم

يفصل التقرير النهائي بين:

**إغلاق الشيفرة:** نطاق التصميم مكتمل، الفروق مراجعة، الفحوص اللازمة نجحت، ولا وظيفة مفقودة في الجرد.

**قبول التشغيل:** Android على الهاتف الحقيقي، والويب، وiOS إن توفرت بيئته، والعمليات التشغيلية الآمنة؛ لكل منها حالة مستقلة.

وجود Blocker في دفع تجريبي أو iOS غير متاح لا يُكتب على أنه فشل تصميم، لكنه يمنع عبارة «كل المنصات والتكاملات مختبرة بالكامل». وجود خطأ جديد في رحلة الحجز أو overflow مؤثر أو تسرب بيانات بعد logout يمنع القبول إلى أن يعالج.

**لا يصدر الوكيل أمر نشر أو GO شامل للإنتاج في هذه المهمة. يسلم نتيجة مصدرية واختبارية محددة النطاق، وينتظر إذن النشر المنفصل.**

# 12. رسالة بدء جاهزة للوكيل

> نفّذ إعادة تصميم UI/UX لتطبيق العميل في `user-app-web` وفق ملف `NIRAB_CUSTOMER_UI_UX_EXECUTION_PLAN.md`، باستخدام المراجع المرفقة للاستلهام فقط وهوية NIRAB الحالية. ابدأ RUI-01 بخط أساس وجرد للمسارات، ثم قدم اتجاهًا واحدًا للرئيسية وخدمة مسعّرة وخدمة عرض سعر للاعتماد المبكر، وبعد الاعتماد واصل RUI-02 إلى RUI-06 بالترتيب. انتبه خصوصًا لتوافق روابط التنقل القديمة، وحماية الباقات عند عرضها كتبويب، والتمييز بين مسار fixed ومسار quote.
>
> **اختبار Android يجب أن يتم على الهاتف الحقيقي المتصل باللابتوب، بمعرّفه الفعلي المحدد في `flutter run -d`؛ ممنوع استخدام المحاكي.** شغّل `lib/main.dart` ودوّن الأدلة الفعلية، ولا تعتبر Preview أو نجاح البناء بديلًا عن اختبار التطبيق على الهاتف. عند تعذر اتصال الهاتف، سجّل Blocker ولا تستبدله بمحاكي.
>
> حافظ على وظائف الحجز والدفع والتسعير والمصادقة وقاعدة البيانات. لا تعدّل Backend أو تطبيقات الفرع والفني، ولا تغيّر التوقيع أو Firebase أو الحزم أو إعدادات الإنتاج، ولا تنفذ migrations أو عمليات مالية حقيقية. اعمل على النسخة المحلية الصحيحة مع حفظ عمل المستخدم وcommits محلية مراجعة؛ لا push ولا نشر. سلّم جرد الشاشات وتقريرًا متدرجًا ونتيجة كل منصة واختبار بوضوح، دون ادعاءات تحقق لم تُنفذ.
