# MKT-04 — Verified financial events

Implemented independent tables: marketing_consents, marketing_subject_consents, marketing_conversion_events, marketing_receipts, marketing_outbox, marketing_integrations, marketing_settings_audit. Migration `2026_11_05_000001_create_marketing_tracking_tables.php` is created and NOT executed. MySQL 8 remains unchanged. `down()` drops only these new marketing tables in reverse order.

`MarketingSourceObserver` implements `ShouldHandleEventsAfterCommit`. Booking/payment/wallet/refund/package source rows are refreshed after commit before recording; rollback never records a conversion. Nothing calls an advertising platform from a payment transaction or makes tracking a prerequisite for booking/payment. Recording failures log only the exception class. Scheduled `marketing:reconcile --days=2` recovers recent post-commit gaps from trusted source rows; extend up to 90 days manually after an outage. Consent bindings are captured at source creation; a historical callback without a binding is deliberately excluded.

One receipt per SHA-256 source key: gateway payment+booking, accountant-approved collection, reviewed transfer or actual customer wallet debit. A gateway charge is allocated across non-wallet group weights, conserving its rounding remainder. `FinancialEventPolicy` requires the paid state and trusted collected sum >= final booking charge. Recurring parents require all visits paid if the parent's paid state is not set; one parent purchase counts all visits once. Native web-CAPI is excluded. Wallet top-ups, prepaid visits, warranty visits and legacy provider subscriptions do not produce customer purchase events. Visit package creation must have the matching actual subscription wallet debit. Each renewed package is a separate sale.

Purchase semantic key = `purchase:booking:UUID` or `purchase:package:UUID`; transaction_id is the same booking/package reference. Refund semantic key = refund:PaymentRefund UUID; only refunded/completed rows with a known original purchase emit a refund. Split/partial refunds keep the original transaction_id and actual returned amount. Subsequent amount adjustments do not rewrite an already emitted purchase: captured-money events remain secondary and the financial ledger stays authoritative.

Outbox uniqueness: platform+event UUID. Statuses: pending -> sent / retry -> dead_letter, or failed with a safe reason (consent denied, missing matching data, provider disabled, unsupported event). Retry count capped at six, exponential delay 2 min to hours. Platform retries reuse event ID and original event time. A shared cache lock prevents concurrent duplicate delivery. Remote acceptance is required before `sent`; it does not prove attribution/reporting in the external dashboard. Disabled or unconfigured integrations never issue a request. Owner-only retry still rechecks consent and expiry.

Read/ack verified-events uses the opaque first-party receipt, not a client-supplied paid flag. Browser/native keeps delivered event IDs across retries; vendor transaction/event IDs provide downstream dedup. Exactly-once external delivery across device/storage loss cannot be guaranteed by an HTTP client; retain event/transaction IDs in all GTM mappings.

Retention: 90 days of payloads/receipts, consent expires in 180 days. Purge clears expired payloads/transaction references and removes delivery rows; opaque UUID/hash tombstones remain to prevent late duplicate callbacks. Revocation clears encrypted attribution and fails unsent messages. No email/phone/IP/coordinates or raw payment references are stored in marketing payloads.
